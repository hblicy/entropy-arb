# 实盘上线前加固设计

**状态：** 已确认（用户要求“按建议修复”）

**日期：** 2026-08-27

## 目标

修复审计中已经复现的实盘阻塞项，不改变当前“Entropy + 一个对冲所、固定额度、静态阈值”的策略范围。

## 设计决策

1. 一次套利只有在两腿结果明确、无错误、两腿均有成交且基础币成交量在容差内匹配时，才计为成功交易。明确取消、拒绝、零成交或不匹配成交均计为执行失败；不匹配成交仍先走现有减仓修复路径。
2. 关机先停止产生新机会，再等待所有已发出的执行任务自然得到明确结果；等待期间周期性记录未完成任务，程序自身不主动取消在途订单任务。
3. 对账在交易后的数据陈旧保护期内被跳过时，必须按剩余保护时间自动重新调度，不能丢失这次对账请求。
4. Lighter 订单频道的增量消息必须满足 `begin_nonce == previous_nonce`；任何不连续都重新订阅。
5. 当前 Hyperliquid 适配器只交易 HIP-3 DEX。根据官方 SDK 的公开兼容问题，HIP-3 下单不发送 `cloid`；请求结果未知时不盲目重发，交由仓位对账恢复。
6. 启动配置对金额、频率、超时、容差和比例做严格边界校验，非法配置立即失败。
7. 实盘依赖使用确定版本或 Git 提交，避免 VPS 重装时得到不同 SDK 行为。

## 验证标准

- 每个修复先有可复现的失败测试，再做最小实现。
- 完整测试在警告视为错误的模式下通过。
- 所有 Python 文件可编译。
- 文档明确 HIP-3 未使用客户端订单 ID，未知结果依赖仓位对账。
- 最终差异无空白错误，且不包含密钥或 `.env`。
